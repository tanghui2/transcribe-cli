# 方案一（状态带驱动）· 完整原型交付说明

文件：`dir-1-final.html` — 单文件 HTML，浏览器直接打开即可，1440×900 模拟窗口 × 8 个界面状态。

---

## 一、这一版的核心主张

**状态带不是装饰，是这个产品的骨架。**

转写是一条流水线：解码 → 识别 → 纪要 → 翻译 → 导出。方案一把这条流水线做成顶部一条贯穿全宽的深色横带，它同时承担三件事：

1. **阶段导航** —— 五格告诉你现在在第几步
2. **进度条** —— 橙色填充宽度就是整体进度（不需要另找一根进度条）
3. **状态指示器** —— 当前格白字 + 呼吸点，已完成绿字，未开始灰字，出错红字

一屏之内看清"做到哪了、还剩多少、卡没卡住"，这是这个工具最核心的信息需求。

## 三、三个设计决定

### 1. 状态带在「流水线」和「组件自检」两种语境下必须区分

自检屏的五格写着 CUDA / 模型 / Ollama / ffmpeg / 磁盘，编号 01–05，和转写屏的「01 解码 / 02 识别…」长得一模一样但完全是两回事。同一排格子承载两种语义，用户会误以为自检也是流水线阶段。

**处理**：自检两屏的编号前缀改为 `组件 01`…`组件 05`，转写屏保持 `01 解码` 不变。

### 2. 「模型未下载」不是错误

模型引导屏的状态带第一格最初是红色错误态。红色在桌面软件里的语义是"出事了"，会让用户以为软件坏了。模型没下载只是**尚未开始**。

**处理**：新增 `todo` 态（中性灰白 `#DDE3EA`），与 `err` 态（红 `#F3A79E`）严格分开。状态栏 LED 也从琥珀改灰。

### 3. 失败不能只报一行红字

场景 08 的修复区给出可复制的完整命令（CUDA PATH 注入顺序 + 模型下载），而不是"请联系客服"。修好之后点「重新检测」再开始转写。

界面同时明确告知降级后果：**CPU 推理速度约为 GPU 的十分之一，3 小时素材要跑一整天**。让用户自己判断值不值得修。

## 四、数据即图形

三屏原本是纯文字表格，检测器直接判"连续多屏只有文字和框 —— 这几屏还没被设计"。补的图都回答一个用户真会问的问题：

| 屏 | 图 | 回答什么 |
|---|---|---|
| 纪要 | 8 条要点的位置与覆盖占比柱状图 | 这几条要点分别讲的是原片哪个位置的什么内容 |
| 导出 | 6 个文件的体积构成横条 | JSON 要占 7 倍体积，要不要勾词级时间戳 |
| 批次 | 整体进度环 + 三个统计 | 12 个文件还要等多久，不用盯着单条任务 |
| 自检 | 健康度环 + 各项检测耗时 | 环境行不行、自检是不是卡住了 |

## 六、规范自检

`design_lint.py check` 结果：**红灯 0**。

第一轮 43 处红灯（16 处正文低于 14px、7 处标签低于 12px、35 处对比度不足），全部修完。

对比度问题的根因不是字号，而是**状态色本身太浅**：
- `--done` 绿 `#1D8A5F` → `#136B49`（白底 3.88 → 5.9）
- `--accent-btn` 橙 `#C2491A` → `#A83A12`（白底 4.42 → 6.4）

深色状态带场景不受这两个色值影响。

## 八、落地建议

**技术选型**：Electron + React（主进程调 Python CLI，子进程管理转写任务）
**或者**：Tauri + Rust 调 Python —— 体积小一个量级

**为什么保留 Python**：转写核心是 faster-whisper + ctranslate2，这是 CUDA 生态里最成熟的一套，重写不划算。GUI 只负责三件事：拖文件、显示进度、预览结果。

**落地顺序**：
1. 先做「转写中」和「导出完成」两屏（覆盖 80% 使用时长），双栏布局 + 状态带
2. 再接「纪要」和「双语字幕」
3. 「批量队列」和「模型引导」最后做

**必须提前解决的**：
- 转写是长任务，进程要能中途取消 —— CLI 需要加 `--cancel` 标志或走 stdin 通信
- 显存独占：第二个实例启动会静默崩溃（无 Python 异常、日志 0 字节、exit=1）。GUI 必须在启动前检测显存占用并给出明确提示
- 多任务排队实际是串行的（显存装不下两个 large-v3），UI 不能让用户以为能并行
